## Alpha diagnosis

The unchanged baseline uses BGRA8, `.bgra8Unorm_srgb`, white material tint, `UnlitMaterial(applyPostProcessToneMap: false)`, transparent blending at opacity 1, no opacity threshold, full-canvas UVs and the existing upright/lane-local mirror transform. A blit copies bytes; it does not change alpha association.

The baseline generator already scales encoded RGB by alpha, but the tested material path also applies alpha during compositing. Feeding it already-associated RGB therefore attenuates fractional-alpha color again. This is not an identity, orientation, Data-copy or byte-order failure.

Four separately generated byte conventions were compared. **No image was merely relabeled.** Let `C` be unassociated sRGB color, `A` alpha, `D` sRGB decoding and `E` sRGB encoding:

| Variant | RGB stored in the BGRA/sRGB texture | Purpose |
|---|---|---|
| Original baseline | `A × C` | Preserve the original encoded-domain premultiplication exactly for body comparisons. |
| Straight | `C`, independent of nonzero A | Test the material's unassociated-color interpretation. Zero-alpha control padding is black. |
| Linear-premultiplied | `E(A × D(C))` | Correctly associate in linear light before storing in an sRGB texture; distinguish this from multiplying encoded bytes. |
| Straight + color dilation | Straight RGB, plus local color extended four texels into zero-alpha padding | Test the narrow interpolation rim separately. Alpha stays zero outside the original content. |

Independent red/half-alpha byte anchors are **128 / 255 / approximately 188** for encoded-premultiplied / straight / linear-premultiplied respectively. Chart colors are regenerated from canonical colors. Body comparisons derive unassociated color from the original quantized synthetic pixels, so small reconstruction quantization is possible; this is not a recommendation to round-trip live camera color through 8-bit premultiplication.

### Controlled measurements

Each camera-tone setting rendered **16 charts**: four byte conventions × light/dark backgrounds × nearest/linear sampling. Each chart has both slots, five alpha levels and three color rows: **480 patch observations per setting**, 960 total. Large flat interiors avoid edge filtering. Uncompressed offscreen RealityKit outputs were read after render completion; UI JPEGs and recording compression are not used for these numbers.

Opaque output depends on the camera/material postprocessing combination. Therefore the alpha-association analysis uses **measured opaque controls**, excluding clipped channels, instead of assuming source RGB equals displayed RGB. Prediction: decode the measured opaque color, multiply by A once, add the background contribution, then encode. A tone-disabled diagnostic isolates this behavior; it is not a proposed production tone setting.

| Stored RGB | Tone-disabled, opaque-calibrated RMSE | Tone-enabled, opaque-calibrated RMSE |
|---|---:|---:|
| Baseline encoded-premultiplied | 0.105370 | 0.121930 |
| Linear-premultiplied | 0.064852 | 0.076435 |
| Straight | **0.001437** | 0.015556 |
| Straight + dilation | **0.001437** | 0.015556 |

Values are normalized sRGB channel errors. The tone-disabled fit uses 132 unclipped fractional-alpha channels per convention; tone-enabled uses 144. Straight's largest tone-disabled error is **0.003676**, less than one 8-bit output step. Clipped controls are excluded explicitly, not presented as accurate fits. The original and linear-premultiplied inputs remain substantially darker than the once-applied-alpha prediction.

**Confirmed:** this tested material path behaves consistently with straight association after its opaque color processing. Correct linear-light premultiplication does not fix a material expecting unassociated color. Flat-interior nearest/linear results were identical, so filtering alone does not explain the broad band.

**Filtering:** straight color with black RGB at zero alpha can still interpolate toward black at the final texture boundary. The separate four-texel RGB-dilation variant addresses that boundary in this synthetic scene without changing alpha or quad extents. It does not justify arbitrary hidden RGB in the currently proposed premultiplied production contract; Kevin/Edo must agree any straight-alpha descriptor and edge policy.

**Color limitation:** enabling normal camera tone mapping restores opaque chart colors close to the input, but fractional-alpha output still deviates from simple linear composition (straight direct-composition RMSE about 0.0159; maximum opaque-calibrated error about 0.0506). Disabling camera tone mapping gives a cleaner association fit but changes opaque colors. Do not ship a tone-map toggle as an alpha fix. The dependency on postprocessing is measured; the private internal processing order and calibrated production color accuracy are not established. Kevin's existing material tone-map choice is preserved.

## Depth and laser ordering: a separate issue

The default material reports **`writesDepth == true`**. A rear glow sample behind known **zero-alpha padding** renders only the background with that setting. Turning depth writes off restores the glow. RGB transparency alone did not guarantee correct occlusion.

However, **depth-write-off alone is rejected**: default transparent sorting lets the rear glow draw over opaque player pixels. This was captured, not hidden or counted as a successful complete correction.

A supported compound candidate was tested:

```swift
material.writesDepth = false
// One shared ModelSortGroup, attached to the actual model entities:
// rear laser core/glow: order 0
// all P1/P2 front/back surfaces: order 1
// front laser core/glow: order 2
```

The group uses the default depth-pass option. Group membership is set explicitly on every model, not assumed to inherit from a root. ReadsDepth, the UV transform, positive world scale, camera and gameplay geometry are unchanged. [Apple's writesDepth API](https://developer.apple.com/documentation/realitykit/unlitmaterial/writesdepth) and installed SDK declarations for ModelSortGroup/ModelSortGroupComponent were inspected. No shader workaround was introduced.

In the tone-enabled light/dark runs, the compound candidate:

- Keeps rear glow visible through zero-alpha padding.
- Makes the sampled opaque player color match the no-laser control, while the depth-only candidate contaminates it.
- Keeps the intended front beam visible over the player.

Example on the dark background: the opaque control is `(1.000, .333, .000)`; depth-off without sorting changes it to `(.949, .675, .114)`; explicit sorting restores `(1.000, .333, .000)`. At padding, rear glow becomes `(.208, .624, .114)` instead of black. These are isolated scene measurements, not universal world-rendering policy.

**Kevin gate:** these ranks describe fixed synthetic layers. A moving beam crossing the player plane, other world geometry, transparent VFX, overlap and the authored RCP scene need an owner-approved presentation policy. This code does not decide collision, damage or whether gameplay considers a beam in front/behind.
